# ADR-0042: Authoring is a host-supplied capability of the public API

**Status:** Proposed — M15 planning only; no implementation
**Date:** 2026-09-19

## Context

M15 requires a package authored, saved and reloaded without hand-editing `.fdt`, through the
public ABI. ADR-0011 requires an editor built on that surface; ADR-0025 made the overlay's
introspection reusable for it. M14 has completed `FoundryApi_v3`, but its content calls are
read-only. There is no source workspace, source writer or package compiler in the table.

There is already a compiler: `tools/fpack/pack.zig` combines `data`'s parser/checker/writer,
asset derivation and confined file access. Copying that into an editor would give one format
two compilers. Putting it in `abi` would violate ADR-0026's translation-only rule. Putting
it in `data` would give a deliberately file-free module a filesystem dependency.

## Decision

**1. Add an optional `author` module at L4**, parallel to `app`, depending on `core`, `data`,
`platform`, `asset`, `mod` and `scene`. `scene` is needed for the compiler's existing built-in
schema registration, not for running a world. `author` has no dependency on `app`, `ui`,
`render2d`, `rhi`, `debug`, `abi` or `script`. Nothing below L4 depends on it.

Move the reusable package compiler out of `tools/fpack/pack.zig` into this module without
changing its language, asset rules, ordering or output. `fpack` remains its CLI host. `author`
also owns the workspace, document revisions, edits, history, diagnostics, saves and candidate
builds. Pure source spans and value emission belong in `data`, beside the existing parser.
Once the ABI is published, fpack's command execution uses it too; its bootstrap supplies the
service and explicit output destinations while its CLI and generated bytes remain compatible.

**2. Publish it in additive `FoundryApi_v4` before building its editor consumer.** V1–v3
remain available and byte-identical. `abi` gains a dependency on `author` and an optional
host-supplied service, not a compiler or workspace implementation of its own. Handles are
generational, inputs copied and bounded, mutations revision-checked, and failures result codes
with structured diagnostics. `editor.md` specifies the surface and implementation order.

The roadmap's "already exposes" means the editor consumes published capabilities: missing
operations must first be implemented and published for every permitted consumer. It cannot
mean "v3 alone", since v3 cannot save content. This clarifies the exit rather than weakening I4.

**3. Filesystem authority comes from the host, never from a package.** The host explicitly
selects a source root, read-only dependency packages and a separate build-output root. Public
calls identify granted workspaces, documents and builds by handles; they cannot nominate an
absolute path or widen a root. A present read-only service refuses writes, an absent service
answers `Unavailable`. Grants are host-wide, as in M14, not a new per-mod security system.

The stock editor loads no native or script code from an opened package. Source editing does
not grant execution consent. Lua binding 1 receives no authoring calls. A native consumer may
use the same surface when its host supplies the capability; native code remains unsandboxed.

**4. The standalone editor is a small host and a separately compiled ABI-only client.** The
host owns engine startup, root grants, renderer/UI lifetime and content loading. The client
owns selection, form presentation and commands; its build imports only standard facilities,
`core` as needed and declarations translated from the installed public header. It cannot
import implementation modules, including `abi` itself. It uses the existing UI table.

Re-host the overlay's content/schema/asset inspection and diagnostic concepts through existing
public calls. Do not import `debug` to gain its borrowed internal pointers, or invent a second
introspection implementation. The editor does not run a game, require an ECS world, or add IPC.

## Consequences

- Tools and native consumers gain the same bounded authoring capability, and the compiler has
  one owner. Ordinary games need not instantiate it or parse source text.
- The source model and runtime model stay distinct: edits never mutate the loaded `Store`.
- The build graph enforces the editor-client boundary, and an external C consumer proves it.
- Cost: a new optional module and ABI version, plus source-document lifetime rules. A CLI
  compiler is simpler than an interactive workspace; that state must live below the ABI.
- Cost: `author` sees `scene` solely for schema registration, following today's compiler.
  Extracting a general schema-provider framework has no evidence and is not part of M15.

## Alternatives considered

- **Editor-specific filesystem/compiler callbacks passed around the ABI:** a private second
  surface; rejected by I4. Host callbacks may implement a published capability, not bypass it.
- **Put all authoring in the editor:** other consumers would not get the mechanism, and compiler
  semantics would drift. Rejected by ADR-0011.
- **Put it in `app` or `data`:** introduces dependencies those modules do not need. A peer at
  L4 preserves their established boundaries.
- **Launch `fpack` as a subprocess for each edit:** leaves document mutation and validation
  outside the public API and adds process/diagnostic plumbing around a callable compiler.
- **Remote editor, new toolkit or dependency:** no need for any of them to meet this exit.

## Revisit if

A measured compile blocks useful interaction despite the stated bounds; an external editor
requires transport; or multiple tools need a smaller schema-registration module. Those are
separate decisions, not reasons to prebuild a job protocol, IPC or plugin system now.
