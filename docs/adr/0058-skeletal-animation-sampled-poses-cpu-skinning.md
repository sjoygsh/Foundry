# ADR-0058: Skeletal animation is sampled poses in an L1 module, skinned on the CPU

**Status:** Accepted 2026-10-01, when the owner requested M24 Step 1
**Date:** 2026-10-01
**Informed by:** ADR-0013, ADR-0022, ADR-0036, ADR-0048, ADR-0051, ADR-0053, ADR-0054, ADR-0055,
ADR-0057, `docs/design/3d.md` §5 and §9, `docs/design/animation3d.md`

## Context

`3d.md` §9 says skeletal animation comes from glTF skins and clips, is translated into
Foundry's own representations, is sampled in simulation at the fixed step, and is skinned on
the CPU first. It does not say which module evaluates a clip, who owns a skeleton, or how a
skinned mesh reaches the screen. `3d.md` §5 also lists "skinned variants" of each shading model
for M24, which a CPU-skinned mesh does not need.

Three things pull on the answer. Sampling must be deterministic (I9), so it must not read a
clock, an entity or a file. Gameplay will want poses that no renderer sees. And every shader
is hand-written per backend (ADR-0049), so each new variant is paid for twice.

## Decision

**Animation evaluation is a new module, `anim`, at L1, depending on `core` alone.**
- It defines `Skeleton`, `Clip` and `Pose` as plain values it borrows, validates by named
  error, and never loads. It holds no time and no playback state: a caller passes a time and a
  buffer, and gets a pose.
- It samples (linear translation and scale, shorter-arc slerp, the rest pose for an untracked
  path), blends two poses, and composes skin matrices in one parents-first pass.
- It contains the linear-blend skinning kernel, over a vertex range, so a caller may chunk it.

**Skeletons and clips are compiled content.** `foundry:skeleton` (`.fskel`) and
`foundry:animation` (`.fanim`) live in `asset`, are generated by the model import as
`<model>.skeleton` and `<model>.clip<i>`, and are handed to `anim` as values, as ADR-0057 hands
collision geometry to `physics3d`. A model record names its skeleton and its clips by name.

**Skinning runs on the CPU, in `render3d`, into vertex data written each frame.** A skinned
mesh keeps its bind streams on the CPU; `render3d` runs `anim.skin` for each visible instance
and draws the result with the existing shaders, in the colour and the shadow pass alike.
**No skinned shader variant exists.** ADR-0054's slots 6 and 7 stay reserved and unbound.

**Playback is the caller's.** Time is seconds derived from a tick count. No engine component
holds animation state until a second consumer shows what it should hold.

## Consequences

- Sampling and skinning are tested with no device, no asset and no entity, and the skinning
  reference is exact arithmetic rather than a pixel tolerance.
- Nothing in any shader changes, on either backend, and the shadow pass needs no work.
- `render3d` gains a dependency on `anim`, and the RHI gains per-frame vertex data.
- **The cost:** every visible skinned instance is skinned on the CPU and uploaded every frame.
  That scales with vertices times instances, and a crowd will exceed it. The design budgets
  and measures it, and names the trigger for GPU skinning.
- A skinned mesh is held twice: bind streams in memory, static streams on the GPU.
- A game that wants animation must write its own playback for now. That is deliberate, and it
  is small: a tick count, a clip and a weight.
- `3d.md` §5's "skinned variants" are not built in M24; the document is corrected at the close.

## Alternatives considered

- **Skin in the vertex shader with a joint-matrix palette.** It is the common approach and
  cheaper per frame. It was rejected for now because it needs a skinned variant of every
  vertex shader on both backends (unlit's four, lit and shadow), an integer vertex format in
  the RHI and a larger per-draw uniform, and it turns the reference test into a readback. `3d.md`
  §9 already chose the CPU first. It returns on a measurement.
- **Put sampling in `scene`, as a system over an engine-declared component.** It gives saves
  and replication a home. It was rejected because it fixes a component's fields before any game
  has shown what playback needs, and ties a pure function to entities. It can be added above
  `anim` without changing it.
- **Put sampling in `render3d`.** One fewer module. It was rejected because a pose is not a
  rendering concept: attachments and hit volumes need it with no renderer.
- **Put the runtime types in `asset` and evaluate above it.** It was rejected because `asset`
  loads and does not evaluate, and because `anim` would then need `asset`, `data` and
  `platform` to test a quaternion interpolation.
- **Keep a node hierarchy in the model and animate nodes.** It would also animate rigid props.
  It was rejected because `3d.md` §3 flattens models on purpose, and a skeleton is the one
  hierarchy a skin needs.

## Revisit if

- `render.skin` is measured above its budget at a character count a real game has. Then GPU
  skinning, and skinned variants, are built, and slots 6 and 7 are bound.
- A second consumer needs playback state the engine should own (a save, a replicated pose, the
  public ABI). Then `scene` declares a component over `anim`.
- A game needs animated rigid props often enough that a skeleton per prop is a burden.
- Gameplay needs skinned vertex positions, which would argue for keeping skinning where it is.
