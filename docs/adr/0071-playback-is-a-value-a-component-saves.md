# ADR-0071: Playback is a value a component saves, and a clip's meaning is a record

**Status:** Accepted 2026-10-31, when the owner requested M34 Step 1; implemented in M34 (2026-11-06, tag `m34`)
**Date:** 2026-10-31
**Informed by:** ADR-0010, ADR-0013, ADR-0041, ADR-0050, ADR-0055, ADR-0058, ADR-0070,
`docs/design/animation-logic.md`

## Context

ADR-0058 left playback to the caller "until a second consumer shows what it should hold". Two
now exist. The sandbox's walker and the court's warden hold the same routine, line for line, and
M34 must save a pose with a world. Its "Revisit if" says that `scene` then declares a component
over `anim`.

Three things pull on the shape. Root motion and events are simulation, so they must run with no
renderer, yet the only path from a model to its clips is `render3d.Content`. A component must
derive and save, and `derive` takes no arrays or pointers. And glTF carries no loop flag, no
events and no root joint, while a clip's records are generated by import, so nothing a person can
edit holds what a clip means.

ADR-0070 has already answered a close question for agents: a value the game owns says what it
wants, and the game moves the body.

## Decision

**Playback is `anim.Player`, a fixed-size value in `anim`, on `core` alone.** It has four channels,
each a clip's name hash, a time anchor, a tick count, a speed and a weight. It reads no clock and
allocates nothing. Time is `anchor + ticks × dt × speed` in `f64`.

**A pose is never state.** It is a function of a player and a rig, so a saved world holds the player
and no pose.

**`foundry:animator` is that value under an engine name,** as `foundry:transform` is `core.Transform`.
A world opts in. `scene` is granted `anim`, not `asset`, and is handed rigs through a small source.
`foundry:root_motion` is derived and unsaved, as `foundry:world_transform` is. A game may also
hold a `Player` directly, with no entity, as the court's warden does.

**What a clip means is a hand-written record, `foundry:animation_set`:** one per model, giving each
clip its loop, speed, root motion and events. None of it enters a clip's bytes, so `.fanim`,
`foundry:model` and the importer don't change, and a mod overrides one record.

**`asset.Rigs` turns a set into an `anim.Rig` below the renderer,** so `asset` is granted `anim`.
A clip is validated once, there, and never on a tick.

**Root motion is a wish.** A clip's motion joint, a root, loses its X, Z and yaw from the pose, and
they are reported as a delta. The game moves the body, and its controller may refuse. A rig also
measures each motion clip's speed, so a body moved by other means can match its feet.

**Events are IDs at a fraction of a clip,** reported from `advance` on the tick, from the newest
channel alone, in time order.

## Consequences

- The copied playback in two samples goes, and a clip stops being validated every evaluation.
- A simulation can use animation with no renderer, on a server or in a replay.
- A save is small and needs no change to `.fsav`.
- `asset`, `scene` and `debug` each gain a grant of `anim`. That is downward, but three more
  modules depend on `Player`'s shape.
- **The cost:** the walker's replay pins move once, because time moves to `f64`.
- **The cost:** a person edits events as text, with fractions, until M111 gives them a timeline.
- **The cost:** a channel count is now a saved shape. More channels are a schema version.
- A body that a controller blocks keeps walking on the spot, until M36 has a game do better.
  *2026-11-09: M36 did ([`animation-ik.md`](../design/animation-ik.md) §9). The game says
  `blocked` as a parameter and the machine decides; a figure that keeps its clip keeps its planted
  feet planted by foot locking.*
- Two representations of a clip's name exist: the string in records, the hash in a player. The
  panel reads the name back from the rig.

## Alternatives considered

- **A component holding only a tick and two clip IDs, with the rest in the game.** Smallest. It
  was rejected because the court's warden, which is not an entity, would keep its own copy, and
  because a generated clip ID changes with a re-export.
- **Evaluate in `render3d`, where `clipOf` already is.** No new grant. It was rejected for the
  reason ADR-0058 rejected sampling there, now sharper: a tick's events and travel would need a
  renderer.
- **Put rigs in `scene`, which CLAUDE.md §4.3 allows to take `asset`.** One grant fewer. It was
  rejected because `scene`'s tests are hermetic and it opens no file, and because a game with no
  world, the court, needs a rig too.
- **Store events and the loop flag in `.fanim`, set through `foundry:model_import`.** One artifact.
  It was rejected because a mod would have to override a generated record or reimport a model to
  move a footstep, and because it changes a compiled format for data no asset holds.
- **Add fields to `foundry:model`'s clip list.** No new record. It was rejected for the same reason:
  a model is generated, and restating one to retime a clip is what `content-schemas.md` §7 warns
  against.
- **Name the clip on the navigation link.** It was rejected because a link is a place, and two
  bodies may cross it differently.
- **Let root motion move the body by itself.** It was rejected because `anim` sees no physics, and
  a body that ignores a controller walks through walls. ADR-0070's seam already answers this.
- **Keep M24's `f32` time, so no pin moves.** It was rejected because a saved value has to run for
  days, and `f32` loses half a tick of resolution in one.

## Revisit if

- M35 needs per-channel state that four nested channels cannot hold within additive versioning.
  **2026-11-06, at M35's close: it did not fire.** `foundry:animator` v2 appends two layers, three
  layer states, eight parameters and a machine as top-level fields, and a v1 save loads and continues
  (`animation-states.md` §8, Step 5).
- `animation.advance` over a real game's animators passes its budget on the i3, which M100's
  parallel systems would then have to answer. **2026-11-06, at M35's close: not on the i3,** where
  32 two-layer machines read 0.039–0.065 ms p95 against 0.10. The M5 reads 0.17–0.23 ms in its
  paced frame, against 0.030 ms for the same work in a tight loop. What the Mac's frame adds is
  M100's, with this revisit.
- A game needs an event to carry data often enough that every game's table is the same table.
- A rig's build time at load is measured as a problem, which would argue for validating at `fpack`.
- A game needs a pose that isn't a function of a player, such as a pose held from a ragdoll. M54
  would then have to save it.
