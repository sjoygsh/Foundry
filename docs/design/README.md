# Design documents

Per-subsystem design written **before** implementing anything non-trivial (development
rule 1). A design doc explains the shape of a system and why, so that implementation is
transcription rather than invention, and so a future session can tell intent from accident.

Not everything needs one. Write one when a subsystem has real structural choices, will be
depended on by several others, or will be hard to change later.

## Owed, in order

Written documents move to the table below. This one is a schedule, not an index.

M5's three design documents are written and nothing is currently owed. Implementation follows
their stated orders — `tilemaps-and-collision.md` §15, `audio.md` §13, `sprite-animation.md`
§10 — and the next document is owed when the next subsystem is.

## Written

| Document | Covers | Decisions worth knowing about |
| --- | --- | --- |
| [`core-memory-and-handles.md`](core-memory-and-handles.md) | Allocator model, generational handles, content ID hashing, logging, assertions, math, time, RNG | Handles are `extern struct` because they cross the C ABI later; null handle is all-zero bits; FNV-1a 64 and PCG32 are **specified in the document**, not delegated to `std`, because both are persisted; simulation time is an integer tick count, never a float |
| [`rhi.md`](rhi.md) | Devices, resources, memory intent, resource states, the frame ring, command recording, pipelines and binding, the validation backend | Every decision taken from the **strictest** API, not the first one implemented: four bind groups because Vulkan only guarantees four, 128-byte inline constants because that is Vulkan's push-constant minimum, `device_local` resources are never mappable so unified memory cannot become a habit, and state transitions are declared at pass boundaries and enforced by the null backend. **Metal backend implemented 2026-09-04**; §9 gained the binding index convention it forced — which is shader-visible, and so a contract each future backend owes its own written version of |
| [`app-and-frame-loop.md`](app-and-frame-loop.md) | The engine loop, subsystem lifecycle, allocator ownership, the log sink, loading content packages | `Engine` is a library you drive, not a framework that calls you back; input is captured once per frame so every simulation step in it sees the same value; teardown is strictly reverse of initialisation; `alpha` is for the render only; the engine consumes a load order and does not compute one, loads package zero through the same call a mod's package uses (I3), and leaves the loaders to the game because it has no `render2d`; hot reload builds a whole new content set and swaps it, at the top of a frame, and publishes a generation counter because a handle survives a reload and anything derived from one does not. **§8 added 2026-09-05** |
| [`render2d.md`](render2d.md) | The game-facing 2D renderer: submission model, coordinate spaces, camera, sprites, batching, buffers, textures and atlases, text, statistics | The **first boundary with users we do not control**, so names here are compatibility decisions; immediate submission with retained resources, so `scene` is not duplicated and the ABI stays simple; `app` owns the frame and the game never sees a render pass; world Y is up and screen Y is down; the sort key is `(layer, submission_index)` and never texture, because reordering translucent sprites is wrong; colour is linear throughout; the renderer keeps **its own retirement queue** rather than trusting the RHI's unimplemented deferred destroy. **Implemented from M2 onward and grown since** — the batcher, camera, atlas and text at M2; the texture loader at M3; `drawTilemap` and `Tiles` at M5; `Region.cell` and the frame-selection functions with it. This document has no Resolution sections: what implementation settled is recorded in `PROJECT_STATE.md`'s milestone entries instead, which is a gap worth closing the next time the renderer is opened |
| [`content-schemas.md`](content-schemas.md) | Schemas, records, packages, the `.fdt` authoring format, the `.fpk` runtime format, load order and override semantics | `data` depends on **`core` alone**, so it cannot open a file — the parser is handed bytes and resolves `@import` through a caller-supplied callback, which makes the whole content pipeline a pure function and every test hermetic; two separate ID spaces for schemas and content; `core` refuses to normalise IDs, so `data` refuses to accept anything that would need normalising; content IDs are bare tokens rather than strings so a typo fails at compile time and `grep` finds every use; directives are `@`-prefixed so a future one can never collide with a mod's schema name. `.fpk` reads in place — explicit little-endian loads at schema-computed offsets, a presence bitmap per block, strings deduplicated and validated once — and its reader is tested by mutating a valid package one byte at a time; a package carries every schema its records use, so it can be read with nothing but itself, and the store reads each record against the copy its own package shipped rather than the registry's newer one. **Parser, schema registry, checker, `.fpk` and the store implemented 2026-09-04**; see its three Resolution sections for what implementation forced, including one decision the store reversed |
| [`assets.md`](assets.md) | Asset identity, ID derivation, the registry, runtime-registered loaders, hot reload | An asset is a content record and its identity is its content ID; a path *derives* an ID at compile time and `fpack` materialises it into the package, so no runtime code can resolve anything by path; derivation transforms nothing, for the same reason `core` refuses to normalise; `render2d` registers the texture loader into `asset` from above, so the dependency points down while the capability points up; the asset schemas live in `asset` so a content compiler can see them without linking a renderer, and a derived record is `.fdt` text put through the same parser and checker as an authored one; `source` is location and never identity, so a package's root is mounted with the registry rather than carried by `data`; a loader's payload is one opaque 64-bit word, which a handle fits in as well as a pointer; zero references means evictable and nothing evicts on a schedule; hot reload swaps behind the handle and a failed reload changes nothing, and nothing recompiles at runtime — `fpack` compiles, the engine reloads. **Implemented in full 2026-09-04 and 2026-09-05** (`asset/`, `tools/fpack/`, `render2d/loader.zig`, `app`); see its three Resolution sections |
| [`platform-interface.md`](platform-interface.md) | Window and surface, events and input, filesystem, dynamic libraries, clock, the null backend | Compile-time backend selection with a `comptime` conformance check; logical size and pixel size are never conflated; input is captured into a per-frame immutable snapshot (an I9 requirement); keys are identified by physical position, with text entry as a separate event. **Implemented 2026-09-03**, both backends — see its Resolution for what implementation changed (chiefly the `Os`/`Platform` split and `std.Io` stopping at this layer) and what SDL3 needed absorbing |
| [`entity-storage.md`](entity-storage.md) | The `scene` module: entities, type-erased component storage, queries, systems, entities in content, world saves | A component type **is a schema**, so identity, versioning, checking and serialization are the ones `data` already has, and a mod declares a component type with `@schema`; the handle is called `Entity` because an entity has no other form; queries iterate the **first** named component's dense array rather than the smallest, so order is a property of the query rather than of the data (I9); a component instance in content is its own record, so a mod overrides one component without restating the entity; a save preserves entity identity exactly — slots, generations and the free list — which is what lets an `Entity` inside component data serialize as a handle with no remap pass, and what makes a reload resume in the iteration order it was saved in; `scene` can read neither a clock nor input, so input reaches systems as data the game wrote down. **All six steps implemented 2026-09-05**, closing M4 (`engine/src/scene/`, and `.fsav` in `save.zig`); see its seven Resolution sections for what that settled, chiefly a component type being identified by a handle rather than an index so a future mod unload cannot leave dangling references, an asset reference in a component being a content id rather than an `AssetHandle` — the same fact as `scene` needing no `asset` dependency — a world being unable to borrow the engine's schema registry because hot reload replaces it, and, following from that, a spawn having to check that a package's schema agrees with the registered one before position-matched deserialization reads the right bytes into the wrong field |
| [`tilemaps-and-collision.md`](tilemaps-and-collision.md) | The `physics2d` module (bodies, shapes, tile grids, broadphase, movement and queries), tilemaps as content, and tilemap rendering | Three things get called "tilemap" and this separates them: a grid of numbers, drawing it, and colliding against it. `physics2d` is **L1 on `core` alone** and holds **no time and no velocity** — a caller says *move this by that* and is told where it stopped, so movement feel stays in the game and the module has no clock to read; the grid is a first-class shape source rather than ten thousand boxes, which is what makes **neighbour-aware face culling** possible and the internal-edge snag exact rather than tolerated; the spatial hash may bucket how it likes but candidates are sorted by handle before use, so the acceleration structure can be replaced without changing a result (I9); a body carries an opaque `u64` rather than an `Entity`, which is the whole of the coupling to `scene`; the grid's bulk is an **asset** because a list of ten thousand integers in `.fdt` is a binary payload in disguise; and M5 adds **no engine-owned component types**, because a `foundry:collider` invented now is a name every mod is stuck with from M7. **Fully implemented, steps 1-7, 2026-09-05/06** (`engine/src/physics2d/`, `engine/src/asset/tilemap.zig`, `engine/src/render2d/tilemap.zig`, and the wiring in `samples/sandbox/`); see its five Resolution sections for what that settled, chiefly that the broadphase's contract is "no false negatives" rather than "the same candidate set" — a larger cell legitimately returns more candidates, so the invariance claim belongs one level up at `World.queryBounds` — that a body is read through a const pointer because a caller moving one by assignment would leave the broadphase describing where it used to be, that the four pair tests collapsed into **one**: every pair reduces to a rounded box and the reduction composes, so box-box, circle-circle, box-circle and a raycast are one static test and one swept test asked different questions, and face culling extends to a corner by requiring both of its faces; that the tilemap schemas and the grid loader live in **`asset`, not `render2d`** — §13's open question 1 answered early by its own trigger, because `fpack` has to check a map without linking a renderer; that `fpack` now emits **two** things, the `.fpk` and a tree of compiled assets, because a tile grid is the first asset kind whose authoring and runtime forms are different files; and that drawing is one pure iterator plus a loop, with the design's `view` parameter dropped because `setView` already names a space for every other draw, culling half-open so a screen-aligned camera does not draw an extra row and column forever, and `foundry:tilemap.layer` grown an optional `empty` at version 2 because a second layer with no way to say *nothing here* paints over the first; and that the last step added **nothing to the engine at all** — a collision world, a `sandbox:collider` and about two hundred lines, all of them in the sample, because §11's "the game wires them" was a claim and this is it being paid |
| [`audio.md`](audio.md) | The audio device in `platform`, the mixer and voices in the new `audio` module, WAV decoding and `foundry:sound` in `asset` | There is a **second thread, Foundry did not create it, and it has a deadline**, and every decision here is downstream of that: state is split by which thread owns it so no field is written by both, two SPSC rings carry commands out and retirements back, and no lock appears anywhere. The device speaks `f32` interleaved and that is not negotiated — a sample-format enum would put a `switch` in the mixer's inner loop for a case that exists because a driver is old; rate and channel count are, because they change what the mixer computes. **The null device is stepped, not threaded**, and the document is explicit that this proves the arithmetic and the protocol but *not* the ring under real concurrency. A `VoiceHandle`'s generation is the answer to stopping a footstep that already ended and killing the door that took its slot. Two lifetime hazards get two mechanisms: the mixer holds the asset reference for a voice's life, and it keeps **its own retirement** — the same answer `render2d` gave for GPU resources — so hot reload cannot free samples out from under the callback. `scene` and `audio` are both L3 and neither depends on the other, so a system *cannot* reach the mixer: that is I9's emit-never-observe rule enforced by the build rather than by documentation. **The mixer opens the device**, so `app` gains no dependency on audio at all. **Design only — not yet implemented** |
| [`sprite-animation.md`](sprite-animation.md) | Clips as content, animation state as a component, and the frame-selection and region-slicing the engine provides | The crossing between `scene` and `render2d` that this document was written to resolve **dissolves once the state is an integer**: `scene` holds a tick count and a frame index and never learns what a texture is, `render2d` turns an index into a region and never learns what an entity is, and the layering could not have let them meet anyway (I7). A float accumulator is refused for three reasons and the deciding one is that it makes "which frame at tick 700?" only *nearly* answerable — the failure that is right in nineteen tests out of twenty; `elapsed_ticks` is chosen over `started_at_tick` because pause and restart are then arithmetic rather than fixups. The component stores a frame **index, not a `Region`**, because a `Region` carries a `TextureHandle` and a component is serialized — the same rule ADR-0021 already applied to textures. The engine's whole contribution is two pure integer functions plus a grid cut built on `Region.sub`; the clip schema and the component are the sample's, for the same reason M5 adds no `foundry:collider`. **Fully implemented, steps 1-3, 2026-09-06** (`engine/src/render2d/animation.zig`, `Region.cell` in `atlas.zig`, `engine/tests/sprite_animation.zig`, and the wiring in `samples/sandbox/`); see its two Resolution sections for what that settled, chiefly that an out-of-range grid cut is **empty rather than clamped** because a stuck animation is indistinguishable from a non-looping clip working while a vanished one sends its author to the clip; that a frame held for zero ticks is never shown and pinning therefore **clamps the tick rather than the index**, so looping and pinning are one walk that settles on the last frame actually displayed; that a clip's numbers reach the system as a **table resolved once per content generation**, because a system is handed the tick and nothing else and so cannot read a record — which is also why advancing a clip *is* a system where moving the player is not; that a looping clip **wraps its own elapsed count by the clip's duration** and a one-shot saturates, with the wrap asserted to be invisible; and that the reload check is an integration test comparing **the UVs a draw call would carry, bit-exactly**, because an epsilon there would pass for the float accumulator §4 refuses |
