# 3D — the shape of Phase 5's second half

**Status: proposed, 2026-09-27. Nothing here is accepted or implemented.** M18 closed Linux, and
Phase 2 finished long ago, so the roadmap's rule that 3D "must not be designed until Phase 2 is
complete" no longer holds it back. This document proposes the architecture and the milestone
order. §11 lists the decisions it needs from the owner. Each accepted decision becomes an ADR,
and each milestone writes its own design before any code, as every milestone has since M3.

## 1. What 3D reuses, and what it adds

The earlier architecture was built so that 3D reuses `core`, `platform`, `rhi`, `data`, `asset`
and `scene` without reshaping them (ADR-0003, CLAUDE.md §4). That is the claim this phase tests.
The additions:

| Layer | Addition | Why it sits there |
| --- | --- | --- |
| L0 `core` | `Quat`, the `Mat4` operations 3D needs (inverse, look-at, perspective), `Transform` (translation, rotation, scale) | Math, like `Vec3` and `Mat4` today; no I/O, no allocation |
| L2 `rhi` | Depth testing, MSAA and resolve, mip chains, cubemaps, instancing; compute later | The capabilities `rhi.md` §12 left out on purpose, and the ones ADR-0003 named |
| L1 `physics3d` | Shapes, queries and a character sweep; no dynamics at first (§7) | Beside `physics2d`, on `core` alone, for ADR-0022's reasons |
| L3 `render3d` | Cameras, meshes, materials, lights, passes, culling | Beside `render2d`, on `core`, `rhi` and `asset`: the second renderer API, not a layer over the first |
| L3 `scene` | A transform hierarchy, as a mechanism (§6) | Entities already live here; a hierarchy is how they relate |
| `tools/fpack` | glTF 2.0 import to Foundry's mesh format | Build-time interchange, never a runtime format (§5) |

**The two rendering boundaries hold** (CLAUDE.md §4.2). Games and mods see `render3d`, never
the RHI. `render2d` keeps drawing UI and 2D content, over a 3D frame or on its own.

## 2. Conventions: compatibility decisions, fixed first

A 3D convention is seen by every mesh, every animation, every save and every mod. Changing one
later breaks all of them. So they are proposed here and frozen by the first 3D milestone:
- **Right-handed, Y up, −Z forward, one unit is one metre.** glTF's convention, which removes a
  whole class of conversion from import.
- **Column vectors and column-major storage,** as `core.Mat4` already has and every shader
  language expects.
- **Rotation is a unit quaternion.** Euler angles appear only in the editor's display.
- **Clip space stays `rhi.md` §9's:** Y up, depth 0 to 1.
- **Reversed-Z,** with a `depth32_float` buffer. The near plane maps to 1, which spreads
  precision where perspective destroys it. It costs one comparison direction and a clear value.
- **Linear lighting, sRGB storage.** Colour textures are `_srgb` formats. Data textures
  (normals, roughness) are not, and the asset kind says which.

## 3. The RHI widens, it does not change

`rhi.md` §12 kept MSAA, mip generation, texture arrays, cubemaps and compute out until a
consumer existed, and no pipeline has yet asked for depth testing. The types already anticipate
some of this: depth formats, depth attachments and a `depth_range`. The work is additive:
- **Depth-stencil state** in the pipeline descriptor: test, write, compare; stencil later.
- **Multisampling:** sample count on textures and pipelines, and `resolve` as the store action
  `rhi.md` §8 shaped the enum for.
- **Mip chains:** uploading every level, and a view of a level range. Generation happens at build
  time in `fpack`, not on the GPU (§5).
- **Cube textures and 2D arrays,** for environment lighting and shadow cascades.
- **Instanced draws.**
- **Compute:** its own milestone step, and only once a pass needs it (skinning or culling
  measured too slow on the CPU). Until then it is not designed in.

**Every capability lands on all three backends in the same step.** The null backend validates
it, Metal draws it, and Vulkan draws it on Windows and Linux. That rule made M13 honest, and it
is cheaper than a later port.

## 4. `render3d`

**A forward renderer first.** Deferred and clustered shading pay off at light counts no Foundry
game has asked for. Forward keeps MSAA cheap and transparency straightforward. It is also the
renderer a 2D-first engine's first 3D game needs. The upgrade to clustered forward has a
measurable trigger: frame time at a stated light count on the target hardware.

The API has the shape `render2d`'s has: begin a frame with a camera, submit, end.
- **Submissions name content IDs and handles, never pointers** (I1, I2). A mesh instance names
  its mesh and material assets, and carries a world transform.
- **Sorting and culling happen in `render3d`.** Opaque front to back, transparent back to front,
  frustum culled on the CPU, jobs split by data-determined chunks (ADR-0036).
- **Passes, in order:** shadow maps, opaque, sky, transparent, then `render2d`'s overlay and UI.
  They are fixed at first. A render graph waits for a second consumer that needs to reorder
  them.
- **HDR and tone mapping:** an `rgba16_float` target, one tone map, and the swapchain's sRGB
  write.

## 5. Meshes, materials and shaders — the decision with the longest tail

**Meshes are assets** (ADR-0021). A new asset kind is compiled to a versioned runtime format
(I8) holding vertex streams, indices, submeshes, bounds and skin data. `fpack` imports glTF 2.0
(`.gltf` and `.glb`), because it is what every tool exports. Its JSON is parsed at build time by
Zig's `std.json`. That is tool interchange, which CLAUDE.md §6 allows. No runtime path parses
JSON or glTF. Textures reuse Foundry's PNG decoder, and `fpack` generates their mip chains.
Compressed GPU formats (BC7 on desktop, ASTC on Apple) are a later decision, with its own
trigger: memory or load time.

**Materials are content records.** A `foundry:material` names a **shading model**, its
parameters and its textures, so a content mod can make a new material with no code (Tier 1).
Where the shaders come from is the question ADR-0015 and ADR-0038 postponed to exactly this
point:

| Option | What it means | Cost |
| --- | --- | --- |
| **A. Engine shading models, hand-written per backend** | Foundry ships a fixed set (unlit, lit, and skinned variants), in MSL and GLSL→SPIR-V as today; materials choose one and set parameters | Every model written twice. No mod-authored shader code. |
| B. One source, cross-compiled | GLSL→SPIR-V with glslang, then SPIRV-Cross (Apache-2.0) to MSL, at build time; shipping the compiler would let mods author shaders | One source. A C++ dependency at build time, and at runtime if mods compile shaders |
| C. Slang | A modern shading language targeting both | The largest dependency, and a language to learn |

**Recommendation: A now, B when mod shader code is due.** A keeps the dependency policy and the
existing tool chain. It gives content mods materials on day one, and it matches ADR-0019
(engine-owned shaders are embedded). ADR-0015's warning still holds: the material system must
not assume every shader is known at build time. So a shading model is a registered entry (I6),
not a switch statement, and a later content-owned shader asset kind plugs into the same
registry.

## 6. The transform hierarchy

M5 decided that the engine owns no component types: a name chosen before any game said what
belongs on it is a name every mod is stuck with. A hierarchy needs the engine to understand
parent links, so it tests that decision. Two options:
- **Engine-declared components:** `foundry:transform` and `foundry:parent`, with a propagation
  system `scene` runs in a documented order (parents before children, then by entity handle, per
  I9). This is simple for games and mods, and it is a permanent public name.
- **A mechanism over game-declared components:** `scene` offers hierarchy propagation over any
  component a game registers as transform-like. No new engine names, but more ceremony for every
  game.

**Recommendation: engine-declared.** A 3D engine without a shared notion of "where is this
thing" pushes every mod to invent one, which is worse for modding (development rule 12) than
one well-chosen name. The name is the decision, and it is the owner's.

## 7. Physics

ADR-0022's argument stands: the deciding issue is I9, not licensing. So:
- **First, collision.** `physics3d` offers shapes (sphere, capsule, box, convex hull, triangle
  mesh), a broadphase, raycasts and shape casts, and a swept character capsule with sliding,
  like `physics2d`'s box. It has no mass and no integration. It covers walking, line of sight and
  picking.
- **Dynamics only when a game needs it.** When stacks, ragdolls or vehicles are wanted, the
  leading candidate is Jolt Physics (MIT). It has a documented cross-platform deterministic
  mode, which answers ADR-0022's objection in a way Box2D could not in 2D. That is its own ADR,
  weighed then against writing a solver.

## 8. Animation, and what the public ABI gains

- **Skeletal animation** comes from glTF skins and clips, and is sampled in simulation at the
  fixed step (I9). It is skinned on the CPU at first; GPU skinning is compute's trigger.
- **The public ABI gains 3D in one additive version** (`FoundryApi_v6`) once the Zig APIs have
  held for a milestone: meshes and materials by content ID, instances, transforms, cameras,
  lights, and physics3d queries. Nothing crosses before then, so mods never see a surface still
  moving. The editor stays a client of that table (I4), and a 3D viewport or scene editor is its
  own later milestone.

## 9. Proposed milestones

Each milestone ends runnable, on macOS/Metal and on Windows and Linux/Vulkan:

| | Milestone | Runnable result |
| --- | --- | --- |
| M19 | **Depth** — core 3D math, the RHI's depth, MSAA, mips, cubemaps and instancing (§3) | A lit, spinning, depth-tested mesh built in code, on all three backends |
| M20 | **Meshes** — the mesh asset kind, glTF import, `render3d`'s camera, culling and unlit draws | A glTF scene from a content package, relocated and hot-reloaded |
| M21 | **Hierarchy** — transforms and parents in `scene`, 3D in the debug overlay | Nested moving objects, inspected live |
| M22 | **Light** — material records, the lit shading model, lights, shadows, HDR and tone mapping | A lit room whose materials a content mod changes |
| M23 | **Collision** — `physics3d` and the character capsule | A first-person walk through that room, colliding |
| M24 | **Animation** — skins, clips, CPU skinning | An animated character from glTF |
| M25 | **Public 3D** — `FoundryApi_v6`, a 3D content mod and a native one | A mod that adds a 3D object and a material |
| M26 | **A playable 3D sample** | The "fully playable 3D game" that ADR-0047 made certification wait for |

A new sample holds the 3D proofs (`samples/` may have more than one). `samples/sandbox` and
`samples/room` stay 2D, and they must keep working at every step.

## 10. Deliberately not here

The following are out, with no date: deferred shading, clustered lighting until its trigger,
global illumination, ray tracing, virtual geometry, terrain, GPU particles, level streaming,
occlusion culling beyond the frustum, D3D12, VR, and a scene editor. Each needs a game asking
for it.

## 11. Decisions for the owner

Nothing in M19 begins until these are answered. Each recommendation is the proposal, not a
decision:
1. **The conventions in §2:** right-handed Y-up metres, quaternions, reversed-Z, linear
   lighting. *Recommended as written.*
2. **Shaders and materials (§5):** engine shading models, hand-written per backend, now;
   cross-compilation when mod shader code is due. *Recommended: A now, B later.*
3. **The hierarchy (§6):** engine-declared `foundry:transform` and `foundry:parent`, or a
   mechanism over game components. *Recommended: engine-declared.*
4. **Physics scope (§7):** collision and a character first; Jolt considered only when dynamics
   are wanted. *Recommended.*
5. **Forward first (§4),** with clustered forward on a measured trigger. *Recommended.*
6. **The milestone order in §9,** and whether the 3D sample is a new `samples/` directory.
   *Recommended as written.*
