# `content/core` — package zero

Foundry's own content package, compiled by `fpack` into `core.fpk` and loaded first.

**This is the whole of what I3 means.** The engine's content goes through exactly the
content-package path a mod uses — the same `fpack`, the same `.fpk`, the same `store.add`,
the same asset registry. There is no privileged loading path, and the way we keep that true
is by always being on the ordinary one ourselves.

What is here is **engine** content, not a game's. Foundry has no game (ADR-0017), and the
sample keeps its own package in `samples/sandbox/content/`. A file lands here when the
*engine* needs it: the debug font does, because the M6 debug overlay will want glyphs and
`render2d` ships none (I5).

## What is in it

| Content ID | File | Notes |
| --- | --- | --- |
| `foundry:fonts.debug` | `fonts/debug.png` | 95 glyphs, 16x6 grid of 8-pixel cells, ASCII 32–126. Generated by `scripts/gen-debug-font.py`, so the glyphs have a source and not only a binary. Ours, so no third-party licence entry (ADR-0016). |

The ID is **derived from the path** and materialised into the compiled package
(ADR-0021): `fonts/debug.png` in a package whose namespace is `foundry` becomes
`foundry:fonts.debug`. Nothing at runtime knows the path. Writing the ID explicitly in a
`.fdt` record would pin it against a future move, and is the fix if one of these is ever
renamed.

## Overriding it

A package loaded after this one and defining `foundry:fonts.debug` replaces it. The mod does
not have to know this directory exists or mirror its layout — it names the ID and nothing
else. That is the property path-identified assets cannot offer, and ADR-0021 records why.
